# bathy v0.1 — Implementation Plan Overview

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement these plans task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Build an open-source, agent-native network discovery engine that turns authorized network questions into bounded scan plans, executes them, and returns structured, evidence-backed findings over MCP.

**Architecture:** A Rust workspace with a hard separation between three layers: (1) a *contract layer* of pure types that generate JSON Schema, (2) a *conventional scanning engine* that never has an LLM on its packet path, and (3) *interface adapters* (CLI, MCP) that are thin translators over the engine. Evidence is content-addressed and immutable; interpretation of evidence into findings is a pure function, which makes results replayable and regression-testable without a network.

**Tech Stack:** Rust 1.85+ (edition 2024), Tokio, serde + schemars, rmcp (MCP), rusqlite, rustls, hickory-dns, etherparse + socket2, wasmtime (deferred to v0.2), blake3, tracing, proptest, cargo-fuzz, criterion.

## Global Constraints

Every task's requirements implicitly include this section.

- **MSRV is tiered, and every tier has a stated cause.** `bathy-types`, `bathy-scope`, `bathy-evidence`, `xtask`: **1.88**, required by the patched `time` (RUSTSEC-2026-0009; the earlier 1.85 floor was an arbitrary edition-2024 minimum that actively blocked the security fix). `bathy-store` and above: **1.95**, required by `libsqlite3-sys`'s build script (`cfg_select!`). Two CI jobs verify both floors — a declared MSRV nothing builds against is not a promise. Develop on stable via `rust-toolchain.toml`.
- **License: Apache-2.0 OR MIT** (dual, Rust ecosystem convention). Every crate declares it.
- **Clean-room.** Do not read, copy, translate, or derive from Nmap source, `nmap-service-probes`, `nmap-os-db`, or any Nmap probe/fingerprint data. All probe and fingerprint data in this project must be independently authored and licensed. This is a legal requirement, not a style preference.
- **`#![forbid(unsafe_code)]`** in every crate except `bathy-packetd`, which may use `unsafe` only for raw socket syscalls and must document every block.
- **No LLM on the packet path.** No crate below `bathy-mcp` may take a dependency on any model/inference client. Enforced by an `xtask` dependency check.
- **No panics in parsing paths.** Any function that consumes bytes from the network, or from a file this project did not write on this run, returns `Result`. `unwrap()`/`expect()`/indexing-slice panics are denied by lint in `bathy-probe`, `bathy-interpret`, `bathy-scope`, `bathy-types`, `bathy-evidence` and `bathy-query` — **every crate `gates::FUZZ_SURFACES` registers as an untrusted-input surface**, which is now a checked relationship rather than a coincidence of two lists.

  **This was aspirational from M1 until M7, and this bullet said otherwise the whole time.** There was no such lint anywhere in the tree — not in either named crate's `lib.rs`, not in `ci.yml`, not in any `Cargo.toml` lint table. Six milestones of code were written in the two crates whose input is by definition chosen by the thing being scanned, against a guarantee that did not exist; the M7 Task 4 threat-model round found the hole and the panic-lint round closed it. Turning the lint on found **43 real hits** across the two crates — among them six `matched_span` computations of exactly the shape that already produced one shipped offset bug (`from_utf8_lossy` offsets used as indices into the original slice) and seven span-corrupting mutants across three review rounds. The reason this paragraph is here rather than deleted is that "a constraint everyone believed and nothing enforced" is the most expensive defect class in this repository, and the record of one is worth more than a clean-looking bullet.

  **What is denied**, at `deny` level, in each covered crate's `lib.rs`: `clippy::unwrap_used`, `clippy::expect_used`, `clippy::indexing_slicing`, `clippy::panic`, and `clippy::arithmetic_side_effects` — the last because an overflowing offset panics in a debug build and silently produces a *wrong span* in a release one, and a wrong span is a false claim about which bytes justified a finding.

  **Test code is exempt by compilation unit, not by a path list.** The attribute is `#![cfg_attr(not(test), deny(...))]`, so under `cargo clippy --all-targets` the library is compiled twice: once as the lib, where the deny is live over every line of production code, and once as the unit-test harness, where it is absent and `unwrap()` stays idiomatic. `tests/` and `benches/` are separate crates that never see the attribute.

  **Exceptions are site-level and must say why.** A crate-level `#![allow]` of any of these lints would reproduce the exact defect this constraint exists to close, so it is refused outright; a site-level `#[allow(..., reason = "...")]` is permitted where the panic is genuinely unreachable, and each one in the tree is additionally backed by a test that fails if its reasoning stops being true.

  **Scope, and how it stays honest.** `bathy-scope` joined this bullet first, at zero measured hits: `ScopeManifest::load` parses a document this project did not write and `allows` then decides whether a packet may be emitted at all, so a panic there is the deny-by-default gate failing. The other three were measured, registered in `gates::PANIC_LINT_UNCOVERED` rather than written into this sentence untruthfully, and closed in the round after: `bathy-types` **37** hits, `bathy-evidence` **15**, `bathy-query` **7** — 59 in three crates that parse an event log written by an older build, a crashed one, or a hand editor, plus every hash this project computes. `PANIC_LINT_UNCOVERED` is now empty, and the `panic-lint-widening` deferral reported itself stale the moment it was (*"`PANIC_LINT_UNCOVERED` is empty, so every untrusted-input crate is covered and this deferral is checking nothing: delete its entry from DEFERRALS"*) and was deleted. What replaced it is stronger than the three crate names it tracked: every non-deferred `FUZZ_SURFACES` entry names the crates its bytes reach, and `check-panics` fails if any of them is outside this sentence — so a *new* untrusted-input surface cannot be registered over an unlinted crate.

  **What the lint cannot see, and what was found by hand instead.** `clippy::indexing_slicing` does not cover `str` indexing (`&s[i..j]`), and does not cover a third-party `Index` impl. A hand sweep of the three newly-covered crates found four such panics the lint would never have reported: `clock.rs`'s `s[i..i + 2]` and `s[i..i + len]` (a validate-then-reparse pair whose second half carried two `expect`s), `ids.rs`'s `&hex[i * 2..i * 2 + 2]`, `store.rs`'s `hex[0..2]`/`hex[2..4]` behind a `.expect("digest renders with prefix")`, and `canonical.rs`'s `map[*k]` — `serde_json::Map`'s panicking `Index`. All five are gone; none of them would have gone red in CI. `clippy::panic` likewise does not see `assert!` or `unreachable!`.

  Enforced by `cargo run -p xtask -- check-panics` (`xtask/src/gates.rs`), which is a `ci.yml` step. It checks the attribute in each covered crate, the shape of every exception, and — in both directions — that the crate list in *this sentence* is exactly the set the tree lints. A bullet that names a crate the tree does not lint is what this constraint was for six milestones; it now fails the build.
- **Determinism claim is scoped.** We claim *deterministic planning* (same request + same scope manifest → same `plan_hash`) and *reproducible interpretation* (same evidence bytes + same engine version → same findings). We do **not** claim reproducible observations; the network is not deterministic. No doc, README, or code comment may make the unscoped claim. `[phrase-rule]`

  **Sentinel convention.** The forbidden phrase is enforced by pattern-matching, so the rule's own statement would otherwise trip its own check — the first CI run would fail on `ci.yml` itself. Any line that legitimately names a forbidden phrase (to define, test, or enforce the rule) must carry the marker `[phrase-rule]`, and every check excludes marked lines. A new forbidden phrase is added in exactly two places: the checker's list, and here.

  The checker is `cargo run -p xtask -- check-phrases` (`xtask/src/phrases.rs`), and `ci.yml` calls it rather than restating it. It used to be three inline greps in `ci.yml` and nowhere else, which is why the AC-2.1 rule stayed red from `89142bf` to the end of M5 while six reports called it green: running the documented gate commands never ran it. **A check nobody can run locally is a check that goes red and stays red.** "Every check excludes marked lines" was also not true of the grep form — only the determinism rule honoured the marker — and is now true by construction for every rule, asserted over the rule list itself by `every_rule_without_exception_honours_the_sentinel`.
- **No gate without a local form.** Five gates lived only inside `ci.yml` as of M5's close-out: `bathy-interpret`'s purity check (AC-4.10) as 32 lines of inline shell whose forbidden-crate list existed nowhere else, both MSRV floor jobs, the `deny` job invoked with no declared check set, and — worst — the "a crate declaring a floor appears in exactly one of the two MSRV jobs" rule, which had **no executable form at all** and three recorded recurrences (`bathy-plan` in M3, `crates/bathy` in M4, `bathy-mcp` in M5, each given a floor and named in neither job). This is the same shape that kept AC-2.1 red for half a milestone: **the gates people run are the gates that have a command.** Each is now `cargo run -p xtask -- check-<something>` (`xtask/src/gates.rs`), and the class itself is closed by `check-ci`, which reads `ci.yml` and fails on any `run:` step that is neither one of those subcommands nor a member of a small, named set of cargo built-ins. The two things that genuinely cannot be xtask subcommands are *installing* a toolchain and *installing* `cargo-deny` — a program that needs the tool cannot be what provides it — so those stay in `ci.yml` and everything checkable about them (which toolchain is pinned, whether `rust-toolchain.toml` is removed, which checks `cargo deny` runs) moved into the checkers.
- **Deny-by-default scope.** No packet is ever emitted to an address that is not inside an active, unexpired scope manifest's allow set and outside its deny set.
- **Canonical hashing.** All hashes (`plan_hash`, evidence digests) use BLAKE3, rendered as `blake3:<64 lowercase hex>`. Structured values are canonicalized with RFC 8785 (JSON Canonicalization Scheme) before hashing.
- **IDs are ULIDs** with a type prefix: `scan_01K…`, `evt_01K…`, `scope_01K…`. Generated only through a `Clock` implementation; never by calling `Ulid::new()` at a use site.
- **All timestamps are RFC 3339 UTC with milliseconds.** Clock access is injected via the `Clock` trait, never `SystemTime::now()` directly, so tests are deterministic. `Clock` lives in `bathy-types` — it is a pure trait with no I/O, and putting it in `bathy-store` would force `bathy-evidence` to depend on a higher layer.
- **Linux first.** macOS is best-effort; Windows is explicitly out of scope for v0.1 (Npcap's license is incompatible with our goals — see `docs/platform-support.md`, Milestone 7).
- **Every finding carries evidence.** A `Finding` cannot be constructed without at least one `EvidenceRef`. Enforce in the type system, not by convention.
- **`README.md` is audited against the branch at every milestone exit.** Three consecutive milestone reviews have found it asserting things the code did not do — M3 found it promising guarantees that did not exist, M4 found it telling operators that probe traffic "carries no identifying payload" while eight probes sent real payloads, and M4's *fix* for that introduced three fresh errors in the same paragraph, including an undercount of connections per port. The recurring cause is that behaviour changes and the operator-facing description does not. So: **every factual claim in `README.md` must be re-verified against the code at each milestone exit, and a claim that cannot be checked in under a minute should be made weaker or deleted.** Overclaiming in the cautious direction is also a defect — understating what we put on someone else's wire is not a safe error.

  Since M5, the claims that are *numbers with a source of truth in the tree* are enforced by `cargo run -p xtask -- check-readme` in CI, because the structural cause of three recurrences is that every other invariant here is enforced by a test that dies and this one was enforced by human attention. That covers connections per open port, the acceptance-criterion and milestone counts, the protocol count and set, which probes put no bytes on the wire, the committed-schema count, the evidence caps, and the "What works today" table against the actual membership of `crates/`. **It does not replace this constraint.** The guarantee sentences — what the scheduler checks and when, what is refused in full, what has no caller — are statements about control flow, are the claims M3's review actually found wrong, and are the ones a checker helps with least. `xtask/src/readme.rs` ends with the written-out list of what stays human-verified; a green `check-readme` means those numbers agree with the tree, never that the README is correct.
- **Manual verification does not close an acceptance criterion.** M4 shipped a cancellability property that a reviewer had confirmed by hand — the measurement was real and correct, and it left no test behind, so a non-cancellable acquire then survived all 98 tests. A criterion is closed by a named test that dies when the code it names is removed, and by nothing else.
- **A fixture that satisfies every branch tests none of them.** The CLI/MCP parity suite compared a `result.query` document whose single fixture endpoint satisfied `--state`, `--service`, `--min-confidence` and `--port-range` simultaneously, so a CLI that *ignored three of the four* passed the entire workspace suite. Only the filter with a narrowing control was actually guarded. Whenever a test exercises a filter, a limit, a branch or a flag, the fixture must **exclude** something the code under test is supposed to exclude, and the test must fail if the input is ignored. This has now appeared four times in different clothes — a guard over two of six schemas, an invariant over nine of eleven fields, parity tests over the two tools already known to differ, and this.
- **A mutation test that does not rebuild is a test of nothing.** A reviewer restored mutated files with `copy2`, which preserves mtime; cargo skipped the rebuild and three results were attributed to code that was never compiled. It caught this itself and re-ran everything, but the trap is silent and the output looks identical. Restore in a way that updates mtime (or `touch` afterwards), and confirm the rebuild actually happened before believing any kill or survival. Never revert a mutation with `git checkout --` — an earlier round did and silently reverted an *uncommitted test*, invalidating two results.
- **`cargo test -p <crate>` can be green while the workspace is red, and this project recommends `-p`.** M5's review scored two mutants — `ScanDiff::retain_substantive` retaining everything, and the fold dropping its `rule_id` write — that survive `cargo test -p bathy-query` and die only under `cargo test --workspace`, because the only tests pinning those behaviours lived in another crate. Neither was a decoration test; the guards were real and they were simply in the wrong place. The disk and time pressure that makes `-p` the recommended loop is also what makes this trap live: **a crate-local green is evidence about that crate's own suite and nothing else.** So: no fix is verified and no mutant is scored until the workspace run is green; and when a `-p` run *cannot* kill a mutant that the workspace run can, that is a missing test in the crate that owns the behaviour, not a reason to stop using `-p`. Both instances above were closed that way rather than noted.
- **Ordering guarantees need a test that fails when the order changes, not one that fails when a step is deleted.** M3's durability inversion (store committed before the log was fsynced) and M5's release-before-publish rule are the same shape: a test that kills *removal* of the release leaves *moving it after the store write* completely unguarded, which is the actual bug in both cases. If the invariant is "A happens before B", assert the interleaving, not the presence of A.
- **A defect found in one file is a defect class until proven otherwise.** A fabricated RFC quotation was corrected in `bathy-interpret` and left standing in `bathy-probe`, leaving the two crates contradicting each other about what RFC 5321 §3.1 says; the branch-wide sweep that followed found a second fabrication in `probes/mysql.rs` and a nonexistent PostgreSQL section. Fix the class, not the instance, and say what you swept.

**Dependency direction is strictly downward.** `bathy-types` depends on nothing internal. `bathy-interpret` depends only on `bathy-types`. `xtask check-deps` enforces this and fails CI on violation.

  This line previously ended "Nothing depends on `bathy-cli` or `bathy-mcp`", and M5 Task 4 found that stale in two ways. There is no `bathy-cli`; the crate is `bathy`. And `bathy` **does** depend on `bathy-mcp`, necessarily: `bathy serve mcp` fronts the server, and the plan's own Task 3 edit #1 assigned that subcommand to Task 4 "in the commit that adds the server it fronts". `xtask`'s layer table already ranked `bathy-mcp` below `bathy` for exactly this edge, so only this sentence was wrong. The rule that actually holds, and that `check-deps` enforces, is the ranking: **`bathy` is the top of the stack and nothing depends on it.**

  M5 Task 4's fix round widened that edge deliberately and recorded the decision here rather than in a commit message. Every `bathy` subcommand now renders the corresponding tool's typed output by calling `bathy_mcp::tools`, because two implementations of one answer is what made the two surfaces diverge in six documents. The functions being called are not MCP-specific — they are the engine's operations over typed inputs from `bathy-types`/`bathy-query`, and `bathy-mcp`'s MCP-specific parts are `server.rs`, `descriptors.rs` and `approval.rs`. So the *name* is now wrong before the layering is: the honest home for `engine.rs` and `tools/` is a crate below both surfaces.

  That move is deferred, on purpose and with a condition. v0.1 ships one binary that always contains both surfaces, so the layering is legal, `check-deps` enforces it, and a twelfth crate landed in a fix round would be an architecture change nobody planned. **The condition that forces it: if `serve mcp` is ever feature-gated, the ops layer must move below both surfaces rather than be duplicated back into `bathy`** — feature-gating it where it stands would take `scan status` out with it. `estimated_runtime_seconds` was the first symptom and has already moved to `bathy-plan`, where a fact about a plan and a budget belongs.

  **That condition is registered mechanically, and this paragraph is not what enforces it** (M5 Task 5, AC-5.39). `xtask`'s `find_deferred_move_violations` fails `check-deps` if the ops layer is still shared out of `bathy-mcp` and anything — a `[features]` table, an optional dependency, a `cfg(feature = …)` in `crates/bathy/src` — makes `serve mcp` conditional. It also reports **itself** as stale if the sharing ends, naming this paragraph and AC-5.39 as the things to delete, because a check that has quietly stopped applying reads as coverage while guarding nothing. The reason it is a check rather than a note is the same reason `ABSENCE_CLAIMS` exists: this milestone found `README.md` denying the existence of the MCP server three times in the commit range that shipped it, with every check green, and prose does not enforce itself.

## Gap Register — spec items deliberately deferred

Recorded here because an audit that does not know what was intentionally left out will report it as a failure. Each line states what the source design document asked for, what these plans deliver, and why.

| Spec item | Status | Rationale |
|---|---|---|
| **ICMP/TCP host discovery** | TCP in M3, ICMP in M6 Task 5 | Unprivileged ICMP is not possible; it needs the same raw-socket capability as SYN scanning, so it belongs with `packetd`. Both halves ship in v0.1. |
| **"Signed/approved target manifests"** | Approval and expiry in v0.1; cryptographic signing **deferred to v0.2** | Signing is only meaningful with a key-distribution and revocation story, and shipping a signature field nobody verifies is worse than shipping none. v0.1 manifests are files with an expiry, validated on every scan. `ScopeManifest` reserves an optional `signature` field so adding verification is not a breaking change. |
| **A2A Agent Card at `/.well-known/agent-card.json`** | **Deferred to v0.2** | The source document itself calls A2A optional and MCP the lower-level interface that coding and automation harnesses use. Shipping one protocol well beats shipping two adequately. |
| **WASM/WASI plugin runtime** | **Deferred to v0.2** | Not in the source document's own v0.1 list. The eight built-in probes are compiled in; the `Probe` trait is the seam a WASM host slots behind later. |
| **OS fingerprinting, UDP breadth, traceroute, evasion modes** | **Out of scope**, per the source document | Explicitly deferred by the design document. Evasion is additionally a permanent non-goal — see M7 Task 5. |
| **IPv6 scanning** | **Out of scope for v0.1**, gap noted | The source document does not mention IPv6 at all, which is a notable omission for a greenfield 2026 scanner. Types are `IpAddr` throughout and `bathy-scope` already refuses IPv6 reserved ranges, so v0.2 is additive rather than a rewrite. Must be listed in the README's limitations. |
| **Measurement-derived port prevalence ranking** | **Deferred to v0.2** | v0.1 ports are an IANA-derived heuristic. This and fingerprint breadth are the two largest gaps between bathy and a mature scanner, and M3 Task 2 and M7 Task 4 both require saying so plainly rather than implying parity. |
| **`Clock` creation** | Trait and implementations (`SystemClock`, `FixedClock`) created in **M2 Task 1** | `bathy-types` is `Clock`'s permanent home (Global Constraint; a pure trait with no I/O, so `bathy-evidence` — which needs it and sits below `bathy-store` in the layer order — can depend on it). Listed under `bathy-types` in the File Structure above because that is where the file lives, not because M1 creates it: no M1 task constructs `Clock`, and M1's own ULID/timestamp fields are supplied externally in tests. M2 Task 1 is the task that actually creates it, and specifies its tests. |

## Audit Procedure (step 3 of the user's workflow)

Every task in every milestone plan carries numbered acceptance criteria of the form `AC-<milestone>.<n>`. These are the audit surface.

To audit an implementation against these plans:

1. Collect every `AC-*` line across all seven plans into a matrix.
2. For each, record: **MET** (with the file:line and the passing test name that proves it), **PARTIAL** (with what is missing), **UNMET**, or **DEVIATED** (implementation differs from plan — record whether the deviation is an improvement, a regression, or neutral, and why).
3. An AC may only be marked MET if there is an automated test that fails when the behavior is removed. "The code looks right" is not evidence.
4. Separately verify the **Global Constraints** above, which are not attached to any single AC. Since the M5 residual wave the whole gate is one runnable set of `xtask` subcommands and needs no reading of `ci.yml` to reproduce: `check-deps`, `check-schemas`, `check-readme`, `check-phrases` (which is where "no `unsafe` outside `bathy-packetd`", "no time or id generation outside `Clock`" and the unscoped determinism phrase are all enforced, marked lines excluded), `check-purity` (AC-4.10), `check-msrv` (the membership rule, plus `--run` to build both floors), `check-deny` (which runs `cargo deny check` with the same four checks CI declares) and `check-ci` (which fails if a future gate is added inline instead of as one of these). `publish-check` is local-only, because the deny list it reads is git-ignored.
5. Report as a table, most severe gaps first. Do not fix during the audit — audit and remediation are separate passes so the audit stays honest.

## Pre-Publication Gates (step 4 of the user's workflow)

- [x] **Name availability confirmed** — checked live in M7 Task 6 (AC-7.31), and the answer changes the shape of this item. **crates.io: `bathy` is already registered to this project's own account** (`0.1.0-alpha.1`, published 2026-08-03, repository `github.com/russell0/bathy`), so publishing v0.1.0 is a version bump on a crate we control rather than a name grab. **The "plausible existing `bathy` crate in the DTrace/USDT space" is refuted**: `GET /api/v1/crates?q=bathy` returns `total = 1`, and that one is ours; the USDT namespace is `usdt`, `usdt-macro`, `usdt-impl`. The fallback order is moot and would not have worked anyway — `fathom` (0.0.0, 2020), `assay` (75k downloads, actively used) and `reckon` (2016) are all taken. **GitHub: `github.com/bathy` is NOT obtainable** — held by a dormant user account created 2013, which also blocks the org namespace; the project stays at `github.com/russell0/bathy`, and no repository named exactly `bathy` has a single star. **DNS: `bathy.dev`, `bathy.io` and `bathy.sh` are all unregistered** (empty `NS`, and `not found` from the `.io`/`.sh` registries and `.dev`'s RDAP). Nothing here forces a rename.
